Delete-Friend Logic (bahut zaroori, exactly is tarah kaam karna chahiye)
Ye mutual/bidirectional removal hai — matlab friendship ek do-tarfa relationship hai, aur delete karna bhi do-tarfa hi hoga:
Case 1 — Agar MAIN kisi friend ko delete karta hoon:
Wo friend meri friends-list se hat jaayega
AUR main bhi uski friends-list se hat jaaunga (uski taraf se dekhne par, use bhi wo dikhega ki main ab uski list mein nahi hoon)
Case 2 — Agar MERA FRIEND mujhe delete kare (unki taraf se):
Main unki friends-list se hat jaaunga
AUR wo bhi meri friends-list se hat jaayenge (mujhe bhi dikhega ki wo ab meri list mein nahi hain)
Summary: Delete kisi bhi ek taraf se ho, effect dono taraf hota hai — ye ek symmetric/mutual relationship hai, ek-tarfa delete possible nahi hai. Jaise hi ek side delete-action leta hai, database mein dono users ke friend-records se ek-doosre ko hataya jaaye (Firestore mein agar dono users ke friend-list-arrays/sub-collections hain, to dono se remove-operation chalani hogi ek hi transaction/batch mein, taaki data-consistency bani rahe)
⚠️ Ranking-Order Logic — ABHI IMPLEMENT MAT KARNA, sirf note/plan kar ke rakho
Leaderboard mein jo ranking-order hai (kaun #1 par aayega, kaun last par) — iske liye ek proposed-idea abhi discussion mein hai, final nahi hai:
Proposed-idea (sirf reference ke liye, code mat karna): Inverse-ranking — jis user ne sabse KAM reels dekhi hain, wo #1/top par aayega; usse thodi zyada dekhne wala #2 par; aur jisne sabse ZYADA reels dekhi hain, wo sabse last/bottom par jaayega. Matlab is "battle" mein "jeetna" = kam scroll karna hai — reverse-leaderboard jaisa concept.
Kya karna hai abhi: Leaderboard-UI (list, rows, rank-badges) poora build kar sakte ho — bas ranking-sorting-algorithm ko abhi hardcode/dummy-order mein rakho ya simple-placeholder-sort use karo (jaise join-order ya random). Actual inverse-ranking-logic ko implement mat karna jab tak main specifically confirm na karoon — ye abhi sirf ek proposal hai, final decision baaki hai.
